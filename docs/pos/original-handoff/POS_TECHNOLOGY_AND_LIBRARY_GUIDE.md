# POS technology, dependency and platform implementation guide

Revision 1.0 — 21 October 2026. Implementation instructions for `ukkera-pos`, using the provisional `BranchPos` YAML namespace. Read with the production architecture revision 3.2, the operational specifications, the domain/API contracts, the implementation task board and the quality plan. This document records public source and artifact research; it does **not** report a successful POS build, test run or production qualification.

## 1. Fixed technology and product boundaries

1. Build the cashier, kitchen, branch management and **complete company administration** experience inside the Compose Multiplatform application. Products, prices, purchasing, permissions, reports, devices and company settings must be usable there. The existing web module-manager is a generation/tooling reference; it is not the required production administration UI and must not become a hidden dependency for ordinary company administration.
2. Share Kotlin domain rules, typed contracts, authorization policies, orchestration and Compose UI across Android, iPhone/iPad, Windows and macOS. Platform adapters own OS services, native permissions, credentials, file locations, printers/scales, packaging and lifecycle. Desktop uses JVM; iOS uses Kotlin/Native. A JVM-only embedded backend cannot satisfy the iOS master requirement.
3. Use Navigation 3, Koin, Coil and Room, with the supported APIs and ownership rules below. Select the latest **jointly compatible stable** dependency set at implementation time, record why any newer version was not selected, then pin it. Do not interpret a registry's `release` field as “stable”: the observed fields include alpha, beta and release-candidate versions.
4. P2pKit RPC is the required LAN transport. The presently published RPC line is a release candidate. Treat it as an explicitly identified integration risk to qualify, not as stable merely because Maven Central serves it. Keep the POS transport boundary replaceable for testing without silently substituting a different production transport.
5. The branch master owns branch transactions, local login and current permissions online and offline. Clients use a typed gateway to the master. A same-device gateway invokes the same command/authentication boundary; it does not let the UI write authoritative DAOs directly. No cloud-login refresh, central lease, central sale authorization or standby acknowledgement enters the sale-commit path.
6. Keep viki-go as the central management/synchronization/reporting platform. Generate new central models from `BranchPos` without modifying existing YAML or overwriting Pos/Item output. Generated CRUD, a client cache, Room, Koin and P2pKit do not implement the required business invariants by themselves.

The implementation foundation owner must refresh this research on the day the first dependency lock is created. Use Maven Central, Google Maven and the Gradle Plugin Portal deliberately; avoid implicit `mavenLocal()`, development repositories, dynamic `+` versions, changing modules and unpinned Git branches in normal builds.

### 2.2 Important dependency findings

**Room 3 is a different API/package line.** Google's Room3 release page identifies `3.0.3` as stable and dates `3.0.0` to 1 July 2026. Its group/package is `androidx.room3`; the runtime/compiler artifact names and Gradle plugin use `room3`. It requires Kotlin code generation through KSP and uses coroutine/SQLiteDriver APIs. SupportSQLite patterns are not the default API. The published `room3-runtime-android:3.0.3` AAR manifest was inspected and declares Android minimum SDK **23**; this does not lower P2pKit's API 24 requirement or establish native-driver runtime compatibility. The live KMP setup page currently contains `3.1.0-alpha01` sample coordinates and mixed historical transaction examples: read the pinned `3.0.3` source/API instead of copying that page verbatim. Stable Room3 documentation describes `withWriteTransaction`; legacy Android-only `withTransaction` snippets must not define the common implementation. The domain contract remains independent of the eventual Room API.

**Navigation versions must be resolved as a graph.** The published UI `1.1.2` POM and metadata variant declare runtime `1.1.7`, lifecycle `2.10.0`, SavedState `1.4.0`, JetBrains Navigation Event Compose `1.1.0`, and Compose components `1.10.0`. Android, desktop and Apple variants point to their own module metadata. These declared baselines can be upgraded by resolution and other dependencies; they are neither the final selected graph nor proof of compatibility with every newer version. Archive `dependencyInsight` or equivalent resolved reports for every target. The same caution applies to Koin Compose ViewModel `4.2.2`, whose POM requests JetBrains lifecycle ViewModel Compose `2.9.6`.

**Koin's preferred compiler path has changed.** Official Koin documentation recommends the K2 compiler plugin for new projects and identifies the old Koin KSP integration as deprecated. Choose one project-wide DI style: **Koin DSL with compiler-plugin checks** is the initial preference. Room's separate KSP2 requirement remains valid. If the newest Kotlin patch cannot be qualified with the plugin, document the supported version selection; do not import old Koin generated-package examples or treat a compiler warning as compatibility proof. Compiler graph checks do not replace runtime scope/lifecycle tests.

**P2pKit release tags are not coordinates.** `samples-v0.8.0-rc6` identifies sample application releases; library coordinates are listed above. The rc6 release record identifies library/sample source `3ef2c6155abd66292011c3775b30fb71d280e9c7`. The observed later repository head was `31969c708cad2caa136393a125f8bfddcc75c6ca`. Do not attribute later source changes or test results to the immutable rc6 binaries. Some RPC documentation still shows rc2 examples; the chosen artifact API and release record govern the integration.

## 4. Platform host design and qualification

The final minimum-OS/CPU matrix is a foundation-spike deliverable, not a guess from the operating-system name. Current CMP `1.12.2` documentation lists only 64-bit platforms: Android API 21, iOS 14, macOS 13 arm64, Windows 10 x86-64/arm64. P2pKit raises the Android floor to API 24 and declares JVM 17/iOS 14 targets. Kotlin `2.4` normally links an iOS 15 minimum unless a documented override is applied. Room, native security, printers and packaging can further restrict the supported combination.

Start qualification with Android API 24+ arm64, iPhone/iPad arm64 with an iOS 15 deployment candidate, Windows x86-64 and macOS arm64. Add emulator/simulator and Windows arm64 coverage where supported by the complete graph. Do not advertise Intel macOS, 32-bit Android, or iOS 14 support just because one component alone supports it. All four required OS families remain release-one obligations; any higher product minimum or additional CPU target must be visible in the final matrix, installation checks and release notes.

| Platform | Service ownership | Required implementation/verification |
| --- | --- | --- |
| Android | Application-owned branch runtime supervised through an appropriate foreground service | Initialize protected identity once from the application; use application context, explicit notification/service type and current platform start restrictions. Validate process restart, denied/revoked permissions, OEM battery behavior, service stop and force-stop separately. WorkManager is not the persistent RPC host |
| iPhone/iPad | Kotlin/Native runtime inside the active application process | Local-network usage description and exact Bonjour declarations in the final plist; prevent automatic idle while hosting. Show the accepted keep-open warning. Background suspension, manual lock, force quit and power loss make the host unavailable; reopening recovers only its still-active authorized role |
| Windows | A separately supervised branch process/service, with UI as its authenticated client | Bundle a qualified runtime/native provider, protected service identity and branch directory ACLs; prove installed service start/restart, ordinary-user UI access and orderly stop. Closing the cashier window must not stop a configured background master |
| macOS | A supported supervised background branch process with an application client | Qualified launch mechanism, Keychain access in the real service context, packaged runtime, hardened-runtime/native linkage and correct cleanup; prove installed behavior under the actual user/service account |

No worker may use a global coroutine or an Activity/ViewModel scope as the branch service lifetime. Master restart checks durable role, intentional-stop marker, epoch, retirement/handover state and storage integrity before accepting clients. An unavailable key or corrupt database produces an explicit recovery state, not a new empty branch database. Screen-awake behavior belongs only to active hosting and is released when that role ends.

Android LAN permission requirements must be evaluated against the final target SDK and OS. P2pKit's current documentation calls out `ACCESS_LOCAL_NETWORK` enforcement for target SDK 37+ on API 37+, in addition to existing LAN/multicast requirements. Verify the current official Android policy, merged manifest and real denial/revocation behavior. Optional hotspot provisioning has separate permissions and must not unnecessarily gate ordinary LAN connections.

## 5. Navigation 3 implementation contract

Use one application-owned navigation model and one production mutation boundary, `AppNavigator`. Feature modules own typed routes and route adapters; presentation composables receive state/callbacks. Do not create a second Nav2 controller, UIKit navigation stack or ad hoc screen enum that owns competing history.

1. Model separate bootstrap/onboarding, branch authentication, branch workspace and company administration security contexts. Opening the administration area does not grant branch cashier authority or reuse a central token for local RPC.
2. Routes contain only bounded typed identifiers and stable serialized names. Never put tokens, a full order, repositories, prices, mutable carts or ViewModels in route arguments. Aggregate feature serializers and route registries explicitly; iOS cannot rely on JVM reflection serialization.
3. Each top-level destination has a bounded independent stack. Tab switching preserves it; active-tab reselection follows the specified pop-to-root rule, subject to the leave guard. Compact, tablet and desktop layouts render the same logical state.
4. Use the pinned Nav3 saveable-state and ViewModel-store entry decorators. Koin resolves entry-owned ViewModels against the entry's owner and stable identity. Feature registration remains modular; the root host does not instantiate every feature's ViewModels.
5. Bind navigation effects and confirmations to active entry, root, selected stack and session generation. Invalidate them on user/company/context change, logout, host detach and root replacement. A delayed action from user A cannot navigate user B.
6. Use one `BackCoordinator` for toolbar, programmatic Back, Android system/predictive Back, iOS swipe, and desktop Escape/Back. Explicit dispositions cover pop, local handling/discard confirmation, blocked operation and platform root exit. Forward/tab/external navigation uses the same relevant leave rules.
7. A guarded or unauthenticated state must not visually reveal a previous protected entry during predictive/interactive Back. Use the pinned public eligibility/entry APIs, not merely a callback that cancels after disclosure.
8. Restore only minimal route history into quarantine. Authenticate, reauthorize every referenced entity under the new session and validate structure/size before rendering it. Do not preserve prior-user screen/ViewModel stores behind a lock overlay. Durable submitted operations are recovered by operation ID, not by serializing an in-memory checkout ViewModel.
9. Keep interactive iOS progress and settlement library-owned. Test Arabic RTL/right-edge and English LTR/left-edge behavior, runtime language change, slow drag, cancellation, rapid input and short fast flicks. Inspect the exact current library source before a public platform-only transition adjustment. Do not copy private recognizer inspection, forced UIKit lifecycle calls, or historical fixed-duration workarounds from older examples.
10. If deep links/notifications are introduced, normalize them to typed bounded intents, validate scheme/host/arguments, session and entity permission, then build a canonical stack through the navigator. Do not register invented production URLs just to demonstrate the plumbing.

Navigation acceptance includes every route's serialization/registration/ownership, duplicate inputs, stack limits, tab restoration, stale events, guards, logout/context switch, accessibility focus, physical iOS gestures and Android predictive Back. Screen snapshots alone are insufficient.

## 6. Koin and coroutine ownership

Use constructor injection and feature-owned modules. Keep domain interfaces free of a DI framework dependency. The chosen DSL and compiler-plugin imports must match the pinned release. Establish the container in the platform/process composition root; recomposition, window creation or cashier login must not repeatedly start/stop the global branch container.

| Lifetime | Examples | End condition |
| --- | --- | --- |
| Platform/process | Sanitized logger, clock adapters, OS facilities, application configuration | Controlled process shutdown |
| Branch service | Authoritative Room database, command dispatcher, local auth registry, RPC host, sync/print schedulers | Explicit service stop/retirement or controlled restart; cashier logout does not end it |
| Client connection | Pinned host connection, read subscriptions, transport status | Host/context change or connection disposal, with explicit reconnect semantics |
| Branch employee session | Effective UI permissions, private query cache, active screen roots | Logout, revocation or account replacement; submitted operation audit identity stays immutable |
| Company administration session | Central admin credentials, company context, admin drafts and permitted reports | Admin logout/company-scope change; separate from employee-session authority |
| Navigation entry | Editor/search/ViewModel/UI effect collectors | Entry removal or security-root reset |
| Individual command | Validated actor/device/context and request dependencies | Command completion; durable work is persisted before losing this scope |

Avoid a singleton mutable `currentUser` used by asynchronous command handlers. Capture and revalidate the command's authoritative actor/session when admitting it, and preserve the original actor on durable retries. Do not let a scoped dependency escape into a longer-lived singleton. Close scopes explicitly, remove listeners and cancel their jobs. Test instances are isolated; no hidden global container causes cross-test leakage.

Use structured concurrency with explicit owners, supervisor boundaries and bounded concurrency. Inject clocks/dispatchers for deterministic tests. Propagate cancellation except where a narrowly defined durable handoff has already occurred; never turn cancellation into success. Canceling a UI coroutine or timing out an RPC does not imply the transaction failed. Query the durable operation result before offering a new financial action.

Separate monotonic deadlines from business timestamps. Persist UTC instants plus branch business-day/time-zone rules, and use monotonic time for in-process retry/deadline measurement. Test DST, manual clock changes, overnight shifts and reboot; do not infer authority from the local wall clock alone.

## 7. Room, SQLite and data integrity

Room is a persistence implementation behind domain ports. The branch master opens the authoritative database; client devices have explicitly non-authoritative, user/company-scoped caches and a protected journal of unresolved command identities. Client cache writes cannot complete sales or manufacture an alternate master.

### 7.1 Schema and transaction rules

- Use one deliberately owned database instance/pool per branch service process and protected platform-specific file locations. Define an exclusive service-instance guard so two processes cannot accidentally serve as the same master. A database file lock is not the distributed fencing protocol for another physical master.
- Generate Room schemas on every actual KMP target using the selected Room major/plugin and KSP2. Commit schema exports. Configure all platform builders consistently; no Android-only schema that the iOS build merely avoids compiling.
- A command transaction includes authorization-sensitive version checks, stock/return/cash constraints, domain records, append-only ledger effects, durable operation outcome, audit linkage and outbox/print/kitchen intents where applicable. Use primary/foreign keys, unique identities and appropriate indexes as enforcement, not only UI validation.
- Coordinate concurrent writers through the database transaction and explicit domain version checks. A Kotlin mutex alone cannot protect against crash/restart, duplicate process or an independent central ingestion worker.
- No network request, printer IO, coroutine delay, manager dialog or remote synchronization inside the database write transaction. Persist an intent atomically and let a bounded worker perform the external action afterward. Printer failure does not roll back a committed sale; reprinting is a distinct traceable operation.
- Pin posted money to bounded integer minor units and explicit exact unit-price/quantity precision. Use checked arithmetic and named rounding/allocation functions. Do not use `Double`, platform-dependent locale parsing or JVM-only `BigDecimal` in shared finance rules. Adopt a portable exact-number library only if the agreed bounds require it and its all-target behavior is verified.
- Persist versioned immutable sale and tax/discount snapshots. Catalog migration, price synchronization and current product deletion cannot rewrite historical receipts or remaining return entitlements.

### 7.2 Durability, encryption and lifecycle

Start with the bundled SQLite driver for a consistent implementation across platforms, subject to successful packaging and native qualification. Configure and measure journal/synchronous/checkpoint behavior appropriate to the promised durable commit, typically WAL with full synchronous durability for the authoritative branch ledger. Verify the effective settings on real opened connections and the selected driver's APIs. A transaction API returning normally is not evidence of power-loss safety for every filesystem/device.

Explicitly test process kill, forced termination, lost response after commit, storage-full, read-only directory, IO failure, corrupted WAL and interrupted migration. On restart, reconcile unresolved operation IDs against durable results before resubmission. Never recover by deleting the database, enabling destructive migration or returning success for an uncommitted operation.

Room and `sqlite-bundled` do **not** themselves establish encrypted database storage. The security owner must record the actual selected mechanism and threat model: OS-protected database location, protected secret fields and, where required, a maintained compatible encrypted driver/database layer. Prove Android, Kotlin/Native iOS and packaged JVM support rather than claiming an Android SQLCipher adapter works everywhere. Do not store encryption keys beside the database or log them.

Keep service secrets and device identity independent of cashier credentials. The branch can resume the same authorized service while the cashier UI stays locked. If platform key accessibility prevents unattended service startup, make that an explicit deployment/recovery state; do not weaken key protection or fabricate a cashier session. Use protected per-platform key facilities and reviewed cryptographic providers. Password/PIN verification requires a reviewed slow password hash, per-account salt, calibrated parameters and local throttling; a short PIN alone must not unlock a directly copied credential database without the designed device protection.

Backups must be consistent snapshots/checkpoints with authenticated encryption, bounded streaming, manifest/version/hash checks and recovery authorization. Copying a live SQLite main file without its WAL/consistency protocol is invalid. Retain operation deduplication, open orders, stock/kitchen progress, cash custody, return entitlement and outbox state. Transfer trust/approved membership through the recovery protocol; never clone a private device identity or revive bearer tokens on the replacement.

### 7.3 Migrations and performance

Before any schema change, preserve the previous schema fixture, write the migration and add fresh-install plus every-supported-version upgrade coverage. Check row counts, keys, relationships, money/quantity values, protected fields and ledger/outbox consistency. Inject failure and prove rollback. Restoration of an older compatible backup must pass the same migration path. Replacing an index is still a schema change.

Use paginated/bounded query projections rather than loading all receipts or full catalogs into memory. Inspect query plans for real predicates and benchmark large catalogs, variant lookups, barcode lookup, remaining stock and report aggregates. Do not add plaintext sensitive lookup columns simply to make indexing easier. Keep write transactions short; monitor pool pressure, database/WAL growth and checkpoint latency during sustained sales and synchronization.

## 8. P2pKit and typed transport integration

Wrap P2pKit behind `BranchGateway`/transport interfaces that are shared by the same-device adapter, RPC adapter and deterministic test adapter. Feature code must not depend on P2pKit internals or create its own peers. One runtime owns the branch host; clients explicitly select an admitted host and never elect a replacement automatically.

- Pin core, LAN and RPC modules to the same verified version; keep public procedure definitions in the shared contract module. Register named/versioned procedures explicitly with Kotlin serializers. Bound request size, item count, nesting, timeout and outstanding calls.
- Use authenticated secure transport with pinned host/device identity and durable trust storage. Discovery is advisory. A changed IP address can update an endpoint under the same identity; discovering another device does not authorize replacing the master.
- P2pKit's peer context identifies the admitted device, not the employee. Resolve local tokens through the master's session registry and check current branch account, permission, resource ownership and policy revision on every sensitive command/read. Ignore a body-supplied user/company/branch identity that conflicts with the authenticated context.
- Persist operation ID before initial submission. Bind durable identity to branch/operation and canonical payload hash; preserve request schema version, original actor and device. Reuse the same ID after timeout, reconnect or app restart. Reusing an ID with a different payload is an error.
- Classify `Committed`, `Rejected` and `UnknownOutcome` distinctly. Authentication failure, permission denial, conflict, insufficient stock, obsolete price/policy, wrong branch/epoch, transport timeout and retriable busy/unavailable states must have typed codes. Do not parse localized exception strings or treat every failure as retry-safe.
- Library retry helpers and in-memory correlation cannot provide exactly-once financial effects. P2pKit documentation explicitly does not supply a durable RPC queue, database or transaction manager. The POS durable result/inbox/outbox design owns those guarantees.
- Notifications are bounded best-effort invalidation hints, not durable events or proof of stock/order completeness. Read current versions and recover deltas/snapshots after gaps. A UI reconnect must not miss a kitchen cancellation or replay a payment because a notification disappeared.
- Core file transfer is not automatically available in the RPC-owned restricted session. Design recovery/catalog attachment transfer as a separately authorized bounded path, or versioned chunked application protocol with its own durability/integrity checks. Do not assume a large database fits one RPC frame.
- Provide paired numeric-endpoint/manual fallback where discovery is blocked, under the same pinned identity. Test guest-Wi-Fi peer isolation, multicast unavailable, IPv4/IPv6/interface changes, denied permissions, reconnect storms, DNS/address changes and master unavailability. No internet signaling or NAT traversal is supplied by P2pKit in this design.
- Current library samples have remaining installed/physical qualification limits. Reproduce required Windows/macOS/iPhone/iPad/Android paths for this application's packaged artifacts. Policy presets such as host capacity limits are not a measured number of POS devices the branch can support.

Never bypass a P2pKit security/provider start failure with an in-memory identity store, permissive trust policy or plaintext fallback. Inspect and fix the underlying platform integration, then repeat the relevant gate.

## 9. Ktor, central administration and Go contracts

Use a shared Ktor client configuration with explicit target engines; initial candidates are OkHttp on Android, Darwin on iOS and a supported JVM engine for desktop. Keep TLS validation enabled, establish bounded connect/request/read timeouts, and sanitize logs. Configure credential propagation per approved origin; a redirect or catalog image URL must not receive a company/admin token unintentionally. Close clients when their owning service/session ends.

Central administration and branch operation are separate authorization contexts even though their screens share one application. Company administrators authenticate with central services for company-wide changes; the branch master receives and activates validated packages asynchronously. Offline admin drafts are visibly pending, not claimed effective across unreachable branches. Branch-local edits use only the permissions/delegation already effective on that master. No queued admin upload bypasses current central authorization when it eventually runs.

Implement typed Kotlin DTOs against a versioned API/JSON contract and local Go endpoints. The YAML generator currently produces central definitions and TypeScript/Go artifacts; do not assume it produces a Kotlin SDK. Either generate Kotlin contracts from an explicitly adopted machine-readable contract or maintain the compact DTO layer with cross-language golden fixtures and compatibility tests.

Shared central contracts must define organization/company/branch scope, pagination/cursors, exact money/quantities, stable IDs, enum evolution, nullability, validation errors, idempotency identity, revision/epoch semantics and durable acknowledgement. Financial retries reuse the original durable **operation ID**, distinct from the order/document ID, transport request ID and current master epoch; one order can legitimately have multiple payment/edit operations. A generic HTTP retry plugin must not replay an unrelated mutation blindly. Keep local and production configurations explicit and prove that switching the central base URL changes no branch authority logic.

Use the existing Go service/toolchain and repository conventions as the starting point, then pin a supported version and compatible dependencies after reviewing the actual `go.mod` and generator snapshot. Do not perform a broad unrelated Fiber/MongoDB/tooling upgrade as a side effect of creating the POS. A MongoDB replica-set local environment is required for transaction tests that depend on multi-document atomicity. Generic model endpoints must not bypass branch operational commands, tenant isolation or ingestion validation.

## 10. Coil, resources and practical UI

Use one deliberately scoped Coil image-loader configuration per allowed security/cache context, not an image loader created for every product card or recomposition. Prefer `AsyncImage` in dense catalog lists, bounded requested sizes, stable keys and explicit loading/error/empty placeholders. Add only required SVG or other decoders after checking the version's supported platforms. Avoid expensive per-item subcomposition where measured scroll performance does not justify it.

Catalog synchronization and image caching are different responsibilities. The authoritative product/price/stock metadata lives in the branch data model. Required offline image assets need an explicit version/hash manifest, authenticated download, storage budget, resumable handling and retention policy; an evictable Coil cache is not a durable catalog. Missing images never prevent search, barcode entry or completing a valid sale.

Partition cache keys/storage by company and resource identity/version, and by user/permission scope for private assets. Include the relevant authorization context without embedding bearer tokens in cache keys or URLs. After user/company switch, clear or replace private memory requests/caches and prevent old completions from rendering into the new session. Test identical URLs used by different companies, updated image versions, expired URLs, revoked access and offline reopening. Enforce maximum decoded dimensions/bytes and disk eviction; keep sensitive supplier documents out of a generic public image cache.

Use Compose Resources and one design system for Arabic/English text, pluralization, numbers, currency, RTL direction, touch/keyboard focus and accessibility semantics. Screens should expose primary tasks first; permissions and activity capabilities reduce visible choices. Show clear branch/master/connection and pending-operation states in normal language. Do not expose implementation terms such as Room, epoch, RPC or outbox to cashiers.

Keep irreversible command state in domain/application state, not only `remember` or a navigation entry. Preserve draft edits explicitly where required. Use manager approval inline without logging the cashier out; the approval is bound to the exact command/payload and expires according to policy. Scanner bursts and repeated taps must not produce duplicate submissions. Test practical narrow-phone, tablet, resized desktop, hardware keyboard, barcode, screen reader, text scale and Arabic receipt flows.

## 11. Library-by-library completion evidence

| Component | Minimum evidence before its work package can be accepted |
| --- | --- |
| Nav3 | Every route registry/serializer/owner test; state-machine and guarded Back cases; stale-session rejection; restoration without protected-frame disclosure; all-platform compile plus physical iOS LTR/RTL gesture matrix |
| Koin | Selected compiler checks pass on every target; startup graph and missing/platform-binding fixtures; two independent user scopes; headless master unaffected by logout; ViewModel/service teardown and retained-resource tests |
| Room/SQLite | Native and JVM execution, transaction atomicity under duplicate/concurrent calls, crash/IO failures, schema export, fresh install/all supported upgrades, backup restore, query-plan/load evidence and encrypted/protected-storage verification |
| P2pKit | Secure pairing/trust persistence, device/user separation, wrong identity/branch rejection, real LAN permutations, timeout/retry/unknown-result recovery, lifecycle/permission cases and installed native-provider tests |
| Ktor/serialization/Go | Cross-language fixtures, scoped authorization, TLS/redirect/header behavior, request limits, retries with stable IDs, durable sync ACK after crash and production/local configuration separation |
| Coil/resources/UI | Company/private-cache isolation, image eviction/offline behavior, bounded decode/memory, no image requirement for sale, English/Arabic semantics and measured list/navigation performance |
| Coroutines/platform services | Bounded queues, cancellation/ownership, repeated start/stop/reopen, no thread/observer/resource leaks, no UI-lifecycle coupling to the master and truthful platform background limits |

Run tests against the implementation boundary they claim to verify. A mocked DAO does not verify SQLite transactions; a mocked gateway does not verify P2pKit; a simulator does not verify a printer or iPhone background behavior; static metadata does not verify a packaged application. Record skipped/unavailable evidence honestly. Use the full quality and acceptance documents for system-wide gates, including higher-order failure combinations.

Upgrade dependencies through a dedicated reviewable change after the first lock: read release notes, inspect compatibility, regenerate/update only intended outputs, rerun affected native/JVM/Android tests and package checks, then update the exact dependency evidence. Do not let parallel feature agents independently change the common version catalog.
