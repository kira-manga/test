settings, not the account's live failed-attempt counters or verifier state.
The policy's employee ID, company/branch scope, revision and complete grant count
are explicit, alongside the existing exact grant details and token lifetimes.
This uses the same read-only configuration presentation as employee enrollment

## Actions and original-result recovery

| Action | Binding and effect |
| --- | --- |
| Disable account | Exact target and account revision; existing disable/revocation transition. |
| Revoke session | Exact account, revision and retained session ID; unrelated sessions are not reattributed. |
| Reset credential | Exact account and credential revisions; protected hash creation and existing session-revocation transition. |
| Revoke device | Exact admission revision; existing protected device revocation service/finalizer. |
| Reactivate credential-bearing account | Exact account, credential, policy and configuration revisions; preserves revoked sessions and requires fresh login. |
| First credential and account activation | Disabled credential-free target and exact four revisions; first hash, enablement and audit are atomic; fresh login required. Native profile qualification remains above. |

The UI first retains/reviews one canonical non-secret command with its original
request ID. It never stages a password. Password arrays are transient and cleared
on all owned exit paths, including a never-started/cancelled coroutine. Compose
input is not saved state; this is not a promise to erase immutable platform input
copies from the VM. Arabic/English presentation and LTR identity fields are
implemented but device/accessibility execution remains unverified.

Non-secret operations may retry only their original ID, with original-audit lookup
first. A dispatched password-bearing request is lookup/cancel-only: another entered password
is never presumed equal to the original secret. NotObserved, denial or unavailable
storage never authorizes a fresh request ID. Pending records survive navigation
and logout; another employee is not substituted for the original actor.

Explicit cancellation writes an immutable no-effect audit at the **same auth-event
key** used by execution. If execution won, cancellation returns the original
Applied event. If cancellation won, subsequent execution of that ID cannot act.
Cancellation never undoes a committed account/device change, payment, cash session
or stock movement. It invalidates its own authorization resource, not unrelated
physical instructions. Actual identity/policy/admission changes retain their own
invalidation. This interaction is not yet physically/native acceptance-tested.

The original request/operator/content digest and ACCOUNT_ADMINISTRATION or
DEVICE_ADMINISTRATION purpose now enter signed runtime history. Generic
PROVISIONING attribution and a newly allocated frame request ID are not used for
these actions. Runtime-history wire tags are unchanged.

Only terminal client records can be explicitly acknowledged/removed. Master
audits remain immutable. An observed Applied event ID is durably retained even
when self-revocation prevents the subsequent current read; no resulting revision
is fabricated. Recovery still needs an authorized current original-actor session.
Self-disable/device revocation may therefore leave client ACK unavailable until
separate authorized identity/device recovery. This is not supervisor relabeling.

## Terminal session denial and scoped permission loss

An authoritative `SESSION_ENDED` from the administration gateway's protected
current check retires the exact original attachment immediately, including on
the directory read path whose compatible public reply remains `Denied`. The
installed retirement sink invalidates the original session fence and lifecycle
in `finally`; failed required cleanup retains its exact holder for later negative
cleanup. A stale adapter cannot retire a successor attachment.

Ordinary directory or original-result permission denial is separate. It clears
denied private presentation while preserving the selected immutable request ID
for protected original-result recovery. Directory access returning alone cannot
restore original action/target details or authorize resubmission. Temporary
unavailability is not proof that the session ended. Previously committed results
and unresolved originals remain intact.
